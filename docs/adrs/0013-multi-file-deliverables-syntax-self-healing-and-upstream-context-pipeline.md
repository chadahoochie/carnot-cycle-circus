# ADR-0013: Multi-File Deliverable Generation, Autonomous Syntax Self-Healing, and Inter-Agent Context Pipeline 📦⚡

## Status
**Accepted** (2026-08-28)

## Context
In the multi-role autonomous engineering pipeline (Technical Product Manager $\to$ Lead Architect $\to$ Software Developer $\to$ Security Engineer & Optimization Engineer $\to$ Principal QA Analyst), realistic enterprise software deliverables require more than single-file monolithic snippets:

1. **Monolithic Code Limitations**: Modern .NET 10 / C# 13 architectures require modular, multi-file code structures (Contracts & Interfaces, Service Implementations, Dependency Injection ServiceCollection Extensions, and xUnit Unit Test Suites). Generating all components in a single concatenated file violates repository layering and clean architecture.
2. **LLM Syntax Fragility**: Language models occasionally produce minor structural syntax flaws (unclosed string literals, unbalanced curly braces, truncated method signatures). Without automated validation and self-healing, syntax errors cascade down the workflow graph to Security, Optimization, and QA reviewers.
3. **Inter-Agent Context Disconnect**: Downstream agents (Architect, Developer, Security, Optimization, QA) need direct visibility into upstream deliverables. An Architect requires the TPM's Product Requirements Document (PRD); a Developer requires the Architect's Architectural Decision Record (ADR) and exact interface contracts; Security, Optimization, and QA analysts require the Developer's exact generated C# source code and unit tests to perform STRIDE audits, memory benchmarks, and traceability matrices.
4. **Artifact Categorization & First-Class PRD Support**: Product Requirements Documents (PRDs) generated by the TPM on Epic decomposition were previously unclassified or treated as generic markdown, rather than first-class deliverables alongside ADRs, Code, Security models, Benchmarks, and QA scorecards.

## Decision
We implement a unified multi-file deliverable engine, autonomous syntax self-healing verification loop, and upstream inter-agent context pipeline:

1. **Multi-File Code Block Parsing (`AgentExecutionEngine.ParseDeliverableArtifacts`)**:
   - Software Developer agent outputs multi-file bundles using tagged code blocks (e.g. ````csharp:I<Domain>Pipeline.cs````, ````csharp:<Domain>PipelineService.cs````, ````csharp:<Domain>ServiceCollectionExtensions.cs````, ````csharp:<Domain>PipelineTests.cs````).
   - The engine automatically extracts each block into a distinct `ArtifactItem` with appropriate names, content types, and metadata.

2. **Autonomous Syntax Verification & Self-Healing Loop (`CSharpSyntaxCheckTool`)**:
   - For all generated C# source files, the engine runs `CSharpSyntaxCheckTool` immediately upon generation.
   - If syntax errors or unbalanced tokens are detected, the engine publishes an alert event to `IAgentEventStream` and dispatches an autonomous remediation prompt to the LLM containing the specific syntax errors and file targets.
   - The healed code bundle is validated and parsed before proceeding downstream.

3. **Inter-Agent Upstream Context Continuity (`GatherUpstreamDeliverables`)**:
   - The engine recursively aggregates deliverables from parent Epics (e.g. PRDs) and direct dependency tickets (e.g. ADRs, C# code, unit tests) via `ITicketStore`.
   - Injects upstream deliverable context directly into role system/user prompts:
     - **Architect**: Receives TPM PRD context.
     - **Developer**: Receives Architect ADR contracts and type signatures.
     - **Security Engineer**: Receives C# code and interface contracts for STRIDE threat modeling.
     - **Optimization Engineer**: Receives C# code methods for BenchmarkDotNet and zero-allocation analysis.
     - **Principal QA Analyst**: Receives C# code and unit tests for test execution mapping and release certification.
   - Injects repository-level architecture patterns from `ICodebaseHarvesterService`.

4. **First-Class PRD Lifecycle & Artifact Categorization (`ArtifactManager` & `ArtifactsHub.razor`)**:
   - Formalized "PRD" categorization across `ArtifactManager`, recognizing `*_PRD.md`, `PRD-*`, and `TechnicalProductManager` deliverables.
   - Added dedicated PRD category filtering, badge counts, and purple styling (`#a855f7`) in the Web UI Artifacts Hub.
   - Updated `TicketItem` with `WithDeliverables(IEnumerable<ArtifactItem>)` for immutable batch artifact attachment.

## Alternatives Considered
- **Single Monolithic File Generation**: Rejected because real-world .NET architectures separate contracts, implementations, DI extensions, and test suites across distinct files.
- **Fail-Fast Error Tripping Without Self-Healing**: Rejected because minor LLM formatting or syntax glitches caused unnecessary full pipeline rejections when an immediate targeted correction prompt resolves the issue in under 2 seconds.
- **Passing Entire Ticket Store to Prompts**: Rejected due to token context window blowouts; targeted dependency traversal (`GatherUpstreamDeliverables`) provides focused, high-signal context without extraneous token consumption.

## Consequences
### Positive
- ✅ Software Developer agents produce clean, modular multi-file C# code bundles matching enterprise repository conventions.
- ✅ Self-healing syntax loop eliminates avoidable compilation failure rejections before code reaches human or downstream review.
- ✅ Strict context continuity across the entire workflow graph ensures downstream reviewers evaluate actual upstream code and architectural decisions.
- ✅ PRDs are tracked as first-class deliverables with dedicated repository synchronization and UI management.
- ✅ 100% deterministic test coverage in `RealExecutionEngineTests` validates all multi-file parsing, self-healing, and context injection paths offline.

### Negative / Trade-offs
- ⚠️ Self-healing loop incurs an additional LLM completion call when syntax errors are detected in live inference mode.
- ⚠️ Upstream deliverable injection increases prompt token payload size, requiring truncation safeguards (capped at 2,500 characters per deliverable) for very large upstream files.
